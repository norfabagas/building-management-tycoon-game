# Timestamp versions and local app updates

The user requested timestamp-only release codes and a Sync action on the home/profile screen when the installed application differs from the current hosted release (2026-10-18). This explicitly permits same-origin checks/downloads of static application files. Gameplay and saves remain offline/local; no account, backend, telemetry or cloud-save sync is added.

## Release contract

`dart run tool/build_web.dart` generates one UTC `yyyyMMddHHmmssSSS` timestamp before compiling. The same 17 digits are compiled into Dart with APP_BUILD, embedded in app_update.js and offline_worker.js, used in the tycoon-app cache name and published in app-version.json. This is an application release identifier, separate from save schema 8/catalog 2 and Flutter's platform package version. Milliseconds distinguish ordinary successive builds; parallel builds in the same millisecond are not supported. Publish the complete output atomically, using the existing Netlify deploy workflow.

app-version.json and offline_worker.js use no-store hosting headers. Version checks request same-origin metadata with no-store and a timestamp query. The worker always sends metadata to the network, never its shell fallback or cache. app-version.json, the asset manifest and worker source are excluded from the offline pack. All actual app assets, including the update bridge, remain available offline. The build command is required: direct flutter build web is not an offline/update release.

## Interface and state

AppUpdateViewModel owns check/sync/retry state; AppUpdateGateway isolates platform operations. Native Android's implementation performs no check and shows no Web update bar. Web uses Dart JS interop with a bundled bridge, without a dependency. The home screen checks initially, on returning from a district, on resume, and every minute while it is the visible resumed route. A compact pinned row displays the installed timestamp with UTC. A green Sync button appears at the top right whenever a valid hosted timestamp differs, including an intentional older hosted release. It remains reachable when the profile list scrolls. Matching versions have no Sync button. Offline/malformed checks show a quiet unavailable status and keep play available; a previously detected mismatch stays available for retry.

Sync displays download status and disables duplicate Sync/profile-entry actions. The bridge rechecks the release, updates the registered worker with updateViaCache none, waits for an installed worker with the requested version, asks it to activate, confirms the controlling worker's version and reloads. Changed deployments require another Sync using refreshed metadata. Failures remain inline and retryable. Downloads/activation have bounded waits. Sync reloads only from the profile screen, away from an active game transaction.

## Cache and save safety

Installation first validates the hosted version, precaches every required resource with HTTP-cache reload, then validates the hosted version again. A missing resource or changed deployment fails installation; the current pack remains active. Only an installed worker receives the explicit ACTIVATE command. It checks all same-scope window clients, including uncontrolled tabs, and refuses activation while another game tab is open. The user sees Close the other game tabs, then tap Sync again. No other player's game is forcibly reloaded. Normal no-client activation remains supported. A tiny new-tab race during the browser activation boundary cannot be eliminated by application code; avoid opening new game tabs during Sync.

Activation removes only obsolete tycoon-app cache packs and claims the current client. The code never clears IndexedDB, SharedPreferences/localStorage, the profile catalog, district records or unrelated caches. No save-schema migration or economy change is required. Partial failed-install packs may remain until the next successful activation removes obsolete packs. This is application-file sync, never save sync.

## First-rollout and platform limits

Clients cached before this feature cannot display a button absent from their old JavaScript. For this first rollout only, let the newer worker download, close all existing game tabs and reopen (a second close/reopen may be necessary). Preserve browser storage. Once this release is installed, later updates use Sync directly. HTTPS or localhost and service-worker support are required for controlled Web updates; unsupported/restricted browsers show a retryable update error and can still use their existing local game. A complete offline pack requires one successful online installation. Browser storage eviction remains outside the application's control. Native Android updates continue through package distribution; physical Android checks depend on SDK/device availability.
