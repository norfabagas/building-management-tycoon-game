# Delete saved profiles

The 2026-10-17 user request adds **Delete** beside Load on every occupied district slot. Empty slots continue to offer New. The confirmation names the full district and slot and states that all buildings, money, tenants and progress will be permanently deleted. Cancel/back leaves the save untouched. Only **Delete permanently** starts deletion. Controls and back dismissal are disabled while it commits; errors remain in the dialog for retry. Success replaces the slot with New and reports which district was removed. Other slots remain available and unchanged.

## Persistence and identity

`ProfileViewModel` coordinates busy state and publishes removal only after `SaveManager.deleteProfile` succeeds. The production SaveManager shares the same GameRepository as DistrictScreen. Its metadata-only constructor remains for legacy metadata adapters/tests; deletion requires a game repository.

To make profile and game deletion atomic, the local Sembast database now holds a version-1, exactly-five-slot `profiles/catalog` record. Its first transaction imports and validates the existing SharedPreferences metadata without changing any game snapshot, name, creation time, slot or balance. Unknown/corrupt metadata or catalog records are preserved and block import instead of being reset. Thereafter this catalog is authoritative; an outdated preference copy cannot restore a deleted profile. SharedPreferences is maintained as a compatibility mirror. A mirror write failure does not undo a committed database operation; a later successful load repairs the copy. A failed database transaction does not publish deletion.

Creation, deletion and catalog reads use database transactions, including operations from separate SaveManager instances sharing the database. Deletion validates the reviewed slot/name/creation-time identity, removes that slot's full `districts` record, clears its catalog entry and writes an anonymous `profile_lifecycle` deletion watermark in the same transaction. It can remove an explicitly selected unsupported game record without deserializing or simulating its contents. Metadata-only legacy districts are deletable too. No backup or undo is created.

The watermark is needed to reject autosaves/actions from an already-open session of the deleted district. Current clients also verify catalog/owner identity before advancing time or applying actions. Reusing the empty slot deletes any orphaned old snapshot and records a new owner. If the device clock moved backwards or the same name is reused, the new creation time is at least one microsecond beyond that slot's deletion watermark. An old confirmation cannot delete a replacement district. Ordinary repeated deletion of the same already-empty generation is harmless.

Full game snapshots remain schema 8/catalog 2; no economy, building/tenant rules, five-slot limit, runtime art, dependency, account or network service changes are introduced. The new metadata catalog and lifecycle records are local to SQLite/IndexedDB. Close older game tabs before activating this release: clients predating these lifecycle checks must not keep writing to the same origin. SharedPreferences cannot be part of a Sembast transaction; its non-authoritative mirror is repaired separately. This is application-level deletion, not a secure device-storage erasure service.
